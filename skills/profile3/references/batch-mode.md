## Пакетный режим: список → ПОСЛЕДОВАТЕЛЬНО, без смешивания

Формат — по одной записи на строку, можно с меткой (`<метка> ГГГГ-ММ-ДД ЧЧ:ММ М|Ж Город`). **Записи НЕ влияют друг на друга.** Для КАЖДОЙ записи:

1. **Валидацию ВСЕХ записей делает ОРКЕСТРАТОР ДО делегирования** (у субагента нет канала к пользователю), и это **ПОЛНЫЙ Шаг 1, включая РЕЗОЛВ города кодом** (`historical_utc_offset` + `geo.resolve`) — «полная, но нерезолвимая» запись («Масква», город-тёзка) иначе умрёт внутри субагента без канала к пользователю. Проверяй полноту И однозначность: чьи данные, дата, ВРЕМЯ (минуты; «00:00»/«12:00» — подозрительные заглушки; двусмысленность времени — по критерию из «Аргументов»), пол, город. **Все вопросы по всем записям — ОДНИМ агрегированным списком** пользователю, не пятью блокировками. Порядок жёсткий: **сначала добери — пропуск записи только после отказа пользователя добрать** (причина — в итоговую таблицу; остальные записи не блокируй). Субагент получает полную однозначную запись + **готовые литералы OFFSET/LAT/LON/NOTE** + пометку **«валидировано оркестратором»** (она гасит повторный триггер «00:00»-заглушки у свежего контекста) и «подтверждает» запись ЭХОМ, без ожидания ответа. **Субагентам запрещено править timezones.py/geo.py и прочие базы**: нерезолвимое → стоп записи и доклад оркестратору; правки баз — только оркестратор, с явного согласия пользователя.
2. **Свой `RUN_ID` и `$TMP`** (Шаг 2). Никогда не переиспользуй `$TMP` другой записи. Своя папка вывода (правила коллизий — в «Куда сохранять»).
3. Прогон Шагов 1→5 ТОЛЬКО по этой записи: 5 калькуляторов → `$TMP/*.json`, `verify_all`, 3 интерпретатора + спот-чеки + синтез → 4 файла + графики + **персист `_*.json` + `_engines.sha`** + PDF.
4. **Числа — ТОЛЬКО из JSON ЭТОЙ записи.** Агентам давай ТОЛЬКО пути `$TMP` этой записи; данные других записей в их промпт не попадают.
5. **Закрой запись** (только когда записаны и 4 `.md`, и персист `_*.json`+`_engines.sha`): в общий индекс — только пути вывода + 2–3 строки сути.

**Изоляция ПО УМОЛЧАНИЮ — свежий контекст субагента на КАЖДУЮ запись** («сделай весь profile3 для ЭТОЙ одной записи»). Субагенту ОБЯЗАТЕЛЬНО дай путь к этому файлу скилла (`$DIR/skills/profile3/SKILL.md`) с задачей «прочитай и исполни для этой записи» — свежий контекст сам «profile3» не знает. Большой список можно оформить как Workflow с циклом по записям — но это тяжелее: подтверди, прежде чем разворачивать.

**Записи между собой НЕ сравниваются** (`4_synthesis.md` сравнивает 3 СИСТЕМЫ одного человека, не людей). Межличностное — только по явной просьбе, ПОСЛЕ независимого расчёта каждого (`/profile3-compare` работает ровно на этой тройке движков).

**В конце** — таблица: запись → папка → 1 строка сути; отдельно записи с хрупкостью к времени. FAIL `verify_all` — это сломанные ДВИЖКИ, а не беда одной записи (тест от записи не зависит): субагент записи движки НЕ чинит — останавливает свою запись и докладывает оркестратору; оркестратор останавливает ВЕСЬ батч, СООБЩАЕТ пользователю и чинит только с его явного согласия (движки и базы городов — канонические, молча их не править); недосчитанное не выдавай.
